# CLAUDE.md 생성

TECHSPEC.md를 바탕으로 프로젝트 작업 지침서(CLAUDE.md)를 작성한다.

## 사전 조건

현재 디렉토리에 TECHSPEC.md가 존재해야 한다. 없으면 중단하고 `/techspec`을 먼저 실행하도록 안내한다.

## TECHSPEC 내용

!`cat TECHSPEC.md`

## 진행 방식

1. TECHSPEC §4.1(기술 스택)을 읽어 스택별 명령어와 규칙을 결정한다.
2. `$ARGUMENTS`가 있으면 ROLE 페르소나로 사용한다. 없으면 아래를 제안하고 선택하게 한다. 복수 선택 가능.
3. ROLE과 스택이 확정되면 아래 템플릿을 채워 CLAUDE.md를 생성한다.

## ROLE 페르소나 제안

| 페르소나 | 관점 |
|----------|------|
| Kent Beck | TDD, Red→Green→Refactor, 작은 단계 |
| DHH | Convention over Configuration, 실용적 단순함 |
| Dan Abramov | 컴포넌트 설계, 관심사 분리, 점진적 복잡도 |
| Rich Hickey | 단순함 우선, 우발적 복잡도 제거 |
| Linus Torvalds | 실용적 성능, 명확한 코드, 불필요한 추상화 금지 |

원하는 페르소나가 없으면 직접 입력할 수 있다.

- P0 테스트(동시성, 중복 방지, 마감 처리)는 반드시 통과해야 한다

## ROLE

## WORKFLOW

### `go` - 구현 사이클

1. **Test First**: 가장 첫 번째 미완료 테스트 케이스를 작성한다
2. **Minimal Code**: 테스트를 통과시키는 최소한의 코드만 작성한다
3. **Lint**: `{{lint 명령어}}` 전체 실행 ({{lint 옵션 설명}})
4. **Run Tests**: `{{test 명령어}}` 실행
5. **Report & Wait**: 결과를 보고하고 사용자 확인을 기다린다

> ⚠️ 이후 자동 진행 금지. 사용자 피드백에 따라 수정하거나 `commit`을 기다린다.

### `commit` - 완료 처리

1. **코드 커밋**: 변경사항을 성격별로 나누어 커밋한다 (리팩토링, {{스택 특성에 맞는 예시}}, 기능 등)
2. **PLAN 체크**: 완료된 항목에 체크박스 표시 + `- Commits:` 줄에 커밋 해시 추가 (매 항목마다 커밋하지 않고, 마일스톤 완료 시 또는 사용자 요청 시 한 번에 커밋)

### `verify` - 마일스톤 완료 후 수동 검증

마일스톤 완료 시 사용자가 직접 확인할 수 있는 검증 명령어를 제안한다.

**제안 범위:**
- {{스택에 맞는 REPL/콘솔}}에서 실행할 수 있는 코드 스니펫
- {{스택에 맞는 DB 확인 방법}}
- 브라우저에서 확인할 수 있는 URL과 기대 동작 (UI 마일스톤인 경우)
- `{{lint 명령어}}`, `{{test 명령어}}` 등 CLI 명령어

**규칙:**
- `commit` 직전 또는 직후에 제안
- 해당 마일스톤에서 구현한 기능에 한정 (이전 마일스톤 내용 반복 금지)
- 복사-붙여넣기로 바로 실행 가능한 형태로 제공

### 명령어

| 명령어     | 동작                                 |
| ---------- | ------------------------------------ |
| `go`       | 구현 사이클 실행 후 사용자 확인 대기 |
| `commit`   | 커밋 및 PLAN.md 체크박스 표시        |
| `status`   | 현재 마일스톤 진행 테이블 + 요약 + 다음 항목 출력 |
| `verify`   | 마일스톤 완료 후 수동 검증 제안      |
| `refactor` | 테스트 통과 후 리팩토링 제안         |

### 원칙

1. **{{프레임워크}}를 믿어라**: 프레임워크가 보장하는 건 테스트하지 마
2. **비즈니스 규칙만 테스트해라**: 그게 바뀌면 앱이 망가지는 것들
3. **{{스택의 테스트 데이터 방식}} 활용**: {{설명}}
4. **동일 성격 검증은 하나의 테스트로 합쳐라**: 필수 필드 3개 → 테스트 1개에서 모두 검증 (필드별 분리 금지)
5. **테스트 내 인라인 로직을 대체하는 {{함수/메서드}}가 추가되면, 기존 테스트도 해당 {{함수/메서드}}를 사용하도록 수정한다**
6. **기대값은 고정값을 사용한다**: 테스트 안에서 쿼리로 기대값을 만들지 말 것 — 테스트는 고정적인 문서 역할을 한다

## CONSTRAINTS

### {{패키지 매니저}} 사용 규칙

- 새로운 {{패키지/gem}}을 사용하기 전에 반드시 {{의존성 파일}}에 존재하는지 확인
- 없으면 코드 작성 전에 추가 필요 여부를 먼저 알려줄 것
- 기존 의존성만으로 해결 가능한지 우선 검토

- 테스트 없이 프로덕션 코드 작성 금지
- 한 번에 여러 기능 구현 금지
- TECHSPEC.md에 명시되지 않은 기술 스택 도입 금지
- 테스트 통과 전 리팩토링 금지
- 미리 추상화 금지 — 중복이 실제로 발생한 후에 추출한다
- {{마이그레이션이 있는 스택만}} 기존 마이그레이션 파일 수정 금지 — 스키마 변경은 항상 새 파일로 처리
- 기능 추가 시 UI에서 접근 가능하도록 버튼/링크를 반드시 함께 제공한다 — 브라우저에서 verify할 수 있어야 한다

### BRANCH RULES

- main 브랜치에 직접 커밋 금지
- 마일스톤 시작 시 `feat/m{번호}-{설명}` 브랜치를 생성하고 전환한다
- 브랜치 생성/전환/머지는 사용자가 직접 수행
- 에이전트는 브랜치 생성/전환/커밋을 수행하되, 머지와 push는 하지 않는다
- 코드 작성 전 반드시 확인: (1) 현재 브랜치가 작업 대상 마일스톤과 일치하는지 (2) 이전 마일스톤 브랜치가 main에 머지되었고 현재 브랜치에 반영되었는지
