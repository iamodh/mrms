# TECHSPEC 생성

프로젝트의 기술 명세서(TECHSPEC.md)를 작성한다.

## 진행 방식

1. `$ARGUMENTS`가 있으면 프로젝트 설명으로 사용한다. 없으면 먼저 묻는다.
2. 아래 질문 목록을 바탕으로 정보가 부족한 항목을 **한 번에 묻는다** (항목별로 나눠 묻지 않는다).
3. 답변을 바탕으로 TECHSPEC.md를 생성한다.

## 수집할 정보

**프로젝트 기본**
- 무엇을 만드는가? (한 줄 설명)
- 누가 사용하는가? (사용자 유형)
- 기존 시스템/방식의 어떤 문제를 해결하는가?

**기능 범위**
- 1단계에서 반드시 구현할 기능은?
- 2단계 또는 나중으로 미룰 기능은?
- 관리자 기능이 있는가?

**기술 스택**
- 프레임워크 / 언어
- 데이터베이스
- 배포 환경
- 프론트엔드 방식 (SPA, SSR, MPA 등)

**제약 조건**
- 동시성, 정원, 마감 등 데이터 무결성 관련 비즈니스 규칙이 있는가?
- 인증/권한 요구사항은?
- 성능 요구사항 또는 예상 트래픽 규모는?

## 출력 구조

수집한 정보를 바탕으로 다음 구조로 TECHSPEC.md를 작성한다.
내용이 불확실한 항목은 TODO로 표시하고 넘어간다.

```
# [프로젝트명] TECHSPEC

## 1. 구현
### 1.1 [사용자 유형] 기능
### 1.2 [관리자 유형] 기능 (있을 경우)
### 1.3 비즈니스 규칙
### 1.4 에러 처리

## 2. 목적
### 2.1 이 프로젝트를 통해 이루고자 하는 목적
### 2.2 2단계 구현 항목

## 3. 작업 목록

## 4. 아키텍처
### 4.1 개발 환경 (기술 스택 테이블)
### 4.2 애플리케이션 아키텍처
### 4.3 배포 아키텍처

## 5. 라우트 설계

## 6. 데이터베이스 스키마
### 6.1 모델 구조 (테이블별 컬럼 + 관계도)

## 7. 핵심 구현 로직
(비즈니스 규칙별로 pseudocode 또는 코드 예제 포함)

## 8. 테스트 전략
### 8.1 필수 검증 항목 (P0)
### 8.2 추가 검증 항목 (P1)
### 8.3 테스트 도구
```

## 규칙

- 기술 선택 이유(왜 이 스택인가)는 TECHSPEC에 넣지 않는다 — `docs/decisions/`에 별도 ADR로 관리
- 2단계 항목은 §2.2에만 기록하고 §1~§7에 섞지 않는다
- 에러 처리 테이블(§1.4)은 반드시 HTTP 상태코드와 사용자 메시지를 포함한다
- 스키마는 컬럼명 / 타입 / 설명 3열 테이블로 작성한다
